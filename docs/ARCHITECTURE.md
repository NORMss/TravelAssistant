# Архитектура

## Модули

```
app                     точка входа, навигация, склейка разделов

core/model              домен: Trip, ItineraryDay, Stop, Place, Fork. Чистый Kotlin
core/common             диспетчеры, часы, Outcome, форматирование
core/designsystem       тема M3 Expressive, движение, плавающие компоненты
core/ui                 composable-блоки, знающие домен (карточка поездки, строка этапа)
core/database           Room: схема, DAO, маппинг, миграции
core/datastore          настройки и ключи моделей
core/data               репозитории — единственный вход к данным для разделов
core/ai                 модели: провайдеры, промпты, формат обмена планом
core/vision             офлайн-распознавание и пакеты регионов
core/testing            фикстуры и правила

feature/today           «Сейчас»: текущий этап, обратный отсчёт, действия
feature/trips           список поездок, создание
feature/itinerary       план: дни, таймлайн, редактор, развилки
feature/places          карта и места
feature/phrasebook      разговорник
feature/assistant       планирование и правка моделью
feature/camera          камера: фотоотчёт и распознавание
feature/catalog         готовые маршруты: каталог, применение
feature/settings        настройки, модели, экспорт
```

Правила зависимостей, которые не стоит нарушать:

* `feature:*` **не зависят друг от друга**. Переход между разделами — это
  добавление ключа в back stack в `app`, а не вызов чужого экрана.
* `feature:*` ходят к данным только через `core:data`. Прямой доступ к DAO из
  экрана превращает смену схемы базы в правку десяти файлов.
* `core:model` не знает про Android. Это позволяет тестировать домен без
  эмулятора и однажды переиспользовать его в KMP без переписывания.
* `core:designsystem` не знает про домен. Компонент, которому нужен `Trip`,
  живёт в `core:ui`.

## Поток данных

```
Room ──► DAO ──► репозиторий ──► ViewModel ──► composable
          (entity)   (домен)      (UiState)
```

Три правила:

1. **Маппинг на границе.** Entity не уезжает выше репозитория: иначе
   переименование колонки правит экраны, а строковые `category`/`status`,
   нужные SQLite, расползаются по всему приложению вместо enum.
2. **Состояние считается во ViewModel.** На экране «Сейчас» это особенно важно:
   «какой этап идёт сейчас» зависит от тикающего времени и часового пояса места,
   и в composable этот расчёт пересчитывался бы на каждой перекомпозиции, а
   проверить его тестом было бы нельзя.
3. **Склейка потоков в репозитории.** День приходит на экран сразу с этапами и
   развилками. Три отдельных потока дали бы кадр, где день уже обновился, а
   этапы ещё нет — на вставке этапа это видно как мигание.

## Время

Самая частая причина ошибок в приложении про путешествия. У нас три разных
«сейчас»: время телефона, время места по плану и время, которое нужно показать.

* Все даты и время в домене — **местные** (`LocalDate`, `LocalTime`), без пояса.
* Пояс хранится у пункта назначения (`Destination.zoneId`), а не у поездки:
  поездка может пересекать несколько.
* `Trip.zoneIdOn(date)` отвечает, по какому поясу идёт день.
* «Сейчас» спрашивают только у `TripClock`, который инжектируется. Благодаря
  этому тест умеет сказать «сейчас 05:12 второго дня», а режим
  «предпросмотр времени» в настройках работает подменой часов, а не ветками в UI.

BeijingTrip решал это проще — константой `Asia/Shanghai`. Для одной поездки
этого хватало.

## Синхронизация: чего ещё нет, но подо что всё готово

Сервера нет. Но у каждой сущности с первого дня есть четыре поля
(`core/model/SyncMeta.kt`, `core/database/entity/SyncColumns.kt`):

| Поле | Зачем |
|---|---|
| `updatedAt` | Разрешение конфликтов last-write-wins |
| `deletedAt` | **Надгробие вместо удаления.** Без него запись, удалённая на одном телефоне, вернётся со второго при следующей синхронизации |
| `remoteRevision` | Что подтвердил сервер; `null` — сервер записи не видел |
| `dirty` | Есть локальные правки, не отправленные наверх |

Два следствия, которые уже работают:

* Во всех запросах есть `deleted_at IS NULL`. Физически строки чистит отдельная
  задача, когда сервер подтвердил удаление.
* Идентификаторы — UUID, выданные на телефоне, а не автоинкременты. Запись
  получает id до любого обращения к сети, и два устройства одного пользователя
  не столкнутся, даже если оба были офлайн.

Добавить эти поля потом — это миграция всей базы и переписанные репозитории.
Добавить сейчас — четыре колонки, которые пока никто не читает.

Выбор бэкенда отложен сознательно (см. [ROADMAP.md](ROADMAP.md), фаза 6).
Схема рассчитана на то, что подойдёт любой: Supabase, Firestore или свой.

## Два слоя данных: личный и публичный

`Trip` — личная поездка: брони, участники, заметки, фотографии.
`TripTemplate` — маршрут, который уезжает к чужим людям.

Это **разные типы**, а не два режима одного. В `TripTemplate` нет полей для
личного, поэтому утечка через публикацию невозможна по устройству, а не по
внимательности. Применение шаблона создаёт поездку; обратного преобразования
нет — публикуемый маршрут собирают заново. Подробно — [SHARING.md](SHARING.md).

## Навигация

Navigation 3. Back stack — обычный `MutableList<NavKey>`, которым владеет
`TravelApp`. Это даёт две вещи, недоступные в Navigation 2: стек можно
прочитать и переписать целиком (переключение разделов не наращивает историю),
и он сериализуется, поэтому переживает убийство процесса.

Ключи — `@Serializable` объекты, а не строки с параметрами:
опечатка в маршруте становится ошибкой компиляции.
