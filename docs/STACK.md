# Стек

Все версии записаны в `gradle/libs.versions.toml` — это единственное место,
где их нужно менять. Ниже — что выбрано и, главное, почему; альтернативы,
которые были рассмотрены и отвергнуты, тоже перечислены: без них через полгода
вопрос «а почему не X» возникнет заново.

## Сборка

| Что | Версия | Почему |
|---|---|---|
| Android Gradle Plugin | 9.4.1 | В AGP 9 поддержка Kotlin встроена — плагин `org.jetbrains.kotlin.android` применять **нельзя**, сборка падает. `CommonExtension` потерял параметры типа: конвенции из примеров под AGP 8 не компилируются |
| Gradle | 9.8.1 | configuration cache включён, в том числе параллельный |
| Kotlin | 2.4.21 | K2, `kotlin.time.Instant` стабилен |
| KSP | 2.3.12 | С версии 2.3.0 нумерация KSP отвязана от версии Kotlin |
| JDK / JVM target | 21 для Gradle, 17 для байткода | 17 — проверенная цель для Android; desugaring включён ради `java.time` на API 26–33 |
| compileSdk / targetSdk | 37 | Не прихоть: `androidx.hilt` 1.4, `material3` 1.5 и `lifecycle` 2.10 отказываются линковаться против 36 |
| minSdk | 26 | Та же граница, что в BeijingTrip. Даёт точные будильники, каналы уведомлений, адаптивные иконки и `java.time` без костылей |

Конвенции сборки лежат в `build-logic` как отдельная включённая сборка. Новый
модуль подключается тремя строками:

```kotlin
plugins { alias(libs.plugins.travelassistant.android.feature) }
android { namespace = "com.normno.travelassistant.feature.<имя>" }
```

Плагин `travelassistant.android.feature` сам подтягивает Compose, Hilt, `core:*`
и тестовые зависимости. Уровни SDK и версия Java записаны в одном месте —
`build-logic/.../Config.kt`.

## Интерфейс

| Что | Версия | Почему |
|---|---|---|
| Compose BOM | 2026.09.00 | Согласованные версии всего остального Compose |
| **material3** | **1.5.0-beta01** | Поднят **выше** версии из BOM осознанно, см. ниже |
| graphics-shapes | 1.1.0 | Нужна `MaterialShapes` |
| material3-adaptive | 1.3.0 | Планшеты, складные, окно на десктопе |

### Почему material3 1.5.0-beta01, а не 1.4.0 из BOM

Проверено распаковкой AAR обеих версий:

* **1.4.0 (стабильная, из BOM)** даёт `MaterialExpressiveTheme`,
  `MotionScheme.expressive()`, `ShortNavigationBar`, `WideNavigationRail`,
  `expressiveLightColorScheme()`.
* **1.5.0-beta01** добавляет ровно то, на чём держится задуманный вид:
  `FloatingActionButtonMenu`, `ToggleFloatingActionButton`,
  `HorizontalFloatingToolbar` / `VerticalFloatingToolbar`, `MaterialShapes`
  (35 форм), `LoadingIndicator`, `ButtonGroup`, `SplitButton`, `ToggleButton`,
  `WavyProgressIndicator` и новый Styles API.

В 1.4.0 этих классов нет вовсе. Плавающая навигация и раскрывающееся меню
действий — не украшение, а основа планировки экрана, поэтому бета принята
сознательно. Вернуться на версию из BOM можно, убрав `version.ref` у
`androidx-compose-material3` в каталоге; из интерфейса при этом исчезнут
плавающая панель и меню FAB.

## Данные

| Что | Версия | Почему |
|---|---|---|
| Room | 2.8.5 | Схемы экспортируются в `core/database/schemas` и лежат в репозитории — по ним проверяются миграции |
| DataStore Preferences | 1.2.1 | Настройки. Proto не нужен: полей мало и они плоские |
| kotlinx.serialization | 1.11.0 | JSON-колонки в Room, обмен файлами, сериализация ключей навигации |
| kotlinx-datetime | 0.8.0 | `LocalDate`/`LocalTime` без привязки к поясу устройства |
| WorkManager | 2.12.0 | Фоновая синхронизация и геокодирование — когда появятся |

**Почему Room, а не JSON-файл как в BeijingTrip.** Там весь набор был 240 КБ и
грузился в память целиком — для одной поездки это было правильное решение.
Здесь поездок много, нужны выборки («активная поездка», «что рядом»),
постраничная подгрузка фотодневника и миграции при изменении модели. JSON-файл
на этом ломается не сразу, а через полгода, когда переписывать уже дорого.

## DI

Hilt 2.60.1 на KSP. Альтернативы: Koin (нет проверки графа на компиляции —
ошибка внедрения всплывает в рантайме у пользователя) и ручное внедрение
(в BeijingTrip работало, но там был один модуль). Hilt выбран ещё и потому, что
его код предсказуем для агентов: это самый распространённый вариант в
документации и примерах Android.

## Карта

`osmdroid` 6.1.20 — тот же, что в BeijingTrip, и по тем же причинам: не нужен
ключ, не нужны сервисы Google, тайлы кэшируются на диск, поддерживаются офлайн-архивы
(`.mbtiles`, `.gemf`). Для универсального приложения без бюджета на API это
единственный честный вариант.

Что рассмотрено и отложено: **MapLibre Native** (13.7.1) — векторные тайлы,
поворот, наклон, легальная загрузка регионов через провайдера. Выглядит лучше,
но требует источника тайлов, то есть ключа и денег. Решение: карта спрятана за
интерфейсом в `:feature:places`, замена реализации не трогает остальное
приложение. См. [ROADMAP.md](ROADMAP.md), фаза 3.

## Чего в стеке нет и почему

* **Retrofit** — сетевых API, кроме моделей, пока нет; OkHttp напрямую хватает,
  а SSE-стриминг ответа моделью Retrofit всё равно не покрывает.
* **Compose Navigation 2** — заменена на Navigation 3, где back stack читается
  и правится как обычный список.
* **Glide, RxJava, LiveData** — Flow и Coil закрывают эти задачи.
* **Firebase Analytics / Crashlytics** — приложение локальное; телеметрия,
  если появится, должна быть выключена по умолчанию и объявлена в Data Safety.
